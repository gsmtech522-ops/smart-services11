How to Unpack Signed boot.img / recovery.img / system.img

Type
Advanced Guide
Level
Advanced
Time
~20 minutes
Applies to
AVB 2.0 signed Android images (Android 8+)
Last updated
YYYY-MM-DD

Modern Android firmware images are signed with Android Verified Boot (AVB 2.0). The signature is stored as a footer appended to the end of boot.img, recovery.img, and a hashtree appended to system.img. Standard unpackers like magiskboot or 7-Zip may fail or produce corrupt output because they read the extra signature data as part of the filesystem. To unpack a signed image, you must first remove the AVB footer with avbtool, then unpack the resulting unsigned image normally [citation:2][citation:15].

Reference

  1. 1. Understand the AVB footer structure

    When a partition is signed with AVB, the tool appends extra data to the image:

    Image typeAVB additionLocation
    boot.img / recovery.imgHash footer (contains SHA256 hash + signature)End of the image
    system.imgHashtree footer (contains dm-verity tree + root hash + signature)End of the image

    The footer tells the bootloader "these bytes must not be modified." For unpacking, we temporarily strip the footer so the image looks like a plain, unsigned filesystem or boot image.

    Note: after modifying the image, you must re-add the footer and re-sign (or use a disabled/blank vbmeta to skip verification). The unpack guide below only covers the unpack half.

  2. 2. Prerequisites

    • Python 3.5+ (for avbtool) [citation:10]
    • avbtool — extract from AOSP or get it from the Magisk tools package
    • magiskboot — for boot/recovery unpacking [citation:14]
    • simg2img — if the image is sparse
    • e2fsck / debugfs — for ext4 system images
    • Linux environment (WSL2 works fine)

    Install avbtool:

    # From AOSP source
git clone https://android.googlesource.com/platform/external/avb
cd avb
python3 avbtool.py --help

# Or use the version bundled with Magisk (in the Magisk APK)
# Extract the APK, look in lib/<arch>/libavb.so or the tools/ folder

  3. 3. Step 1 — Check if the image is AVB-signed

    Use avbtool to inspect the image and confirm the footer exists:

    python3 avbtool.py info_image --image boot.img

    Output will show Footer version: 2.0, Original image size, and the algorithm (e.g. SHA256_RSA4096). If it errors with "not an AVB image", the image is not signed — skip to Step 3.

  4. 4. Step 2 — Remove the AVB footer

    avbtool has a dedicated command to strip the footer and restore the image to its original (unsigned) size [citation:15]:

    python3 avbtool.py erase_footer --image boot.img --output boot_unsigned.img

    For system.img, use the hashtree variant:

    python3 avbtool.py erase_footer --image system.img --output system_unsigned.img

    Why erase_footer? It trims the image back to its declared original size, removing the hash/hashtree and signature. The result is a clean unsigned image you can unpack normally.

  5. 5. Step 3 — Unpack boot.img / recovery.img

    Once the footer is removed, use magiskboot to unpack [citation:14]:

    Create a working directory:

    mkdir boot_unpack && cd boot_unpack
cp ../boot_unsigned.img .
magiskboot unpack boot_unsigned.img

    Output files:

    kernel
ramdisk.cpio
second
dtb
extra
header

    Extract the ramdisk:

    mkdir ramdisk_out
cd ramdisk_out
cpio -idmv < ../ramdisk.cpio

    You now have full access to init, init.rc, sbin/, and other ramdisk files.

    magiskboot error? if magiskboot unpack fails on the unsigned image, the image may use a vendor-specific header. Try Android Image Kitchen (AIK) instead — see the related guide.

  6. 6. Step 4 — Unpack system.img

    System images require a different workflow because they are filesystems, not boot images.

    Step A — Check if the image is sparse:

    file system_unsigned.img
xxd -l 4 system_unsigned.img

    If magic is 3AFF26ED, it is sparse. Convert to raw [citation:6]:

    simg2img system_unsigned.img system_raw.img

    Step B — Check the filesystem type:

    file system_raw.img
# ext4 → "Linux rev 1.0 ext4 filesystem data"
# EROFS → "EROFS filesystem"

    Step C — Extract ext4:

    mkdir system_extract
sudo mount -o loop,ro system_raw.img system_extract
# or use debugfs without mounting:
# debugfs -R "rdump / system_extract" system_raw.img

    Step C — Extract EROFS:

    sudo fsck.erofs --extract=./system_extract system_raw.img

  7. 7. Step 5 — What next? (Repack & re-sign)

    After modifying the extracted files, you must repack and either re-sign the image or disable AVB:

    Option A — Repack and flash with AVB disabled (unlocked bootloader):

    # Repack boot
magiskboot repack boot_unsigned.img new-boot.img

# Flash with disabled vbmeta
fastboot --disable-verity --disable-verification flash vbmeta vbmeta.img
fastboot flash boot new-boot.img

    Option B — Re-add AVB footer and re-sign (requires OEM keys):

    # Add hash footer back
python3 avbtool.py add_hash_footer \
  --image new-boot.img \
  --partition_name boot \
  --partition_size 33554432 \
  --key /path/to/oem_key.pem \
  --algorithm SHA256_RSA4096

# Rebuild vbmeta with new descriptors
python3 avbtool.py make_vbmeta_image \
  --output vbmeta_new.img \
  --include_descriptors_from_image new-boot.img \
  --key /path/to/oem_key.pem

    OEM keys are private. You cannot re-sign with the manufacturer's key unless you extracted it (rare, and usually illegal). For unlocked bootloaders, disabling AVB (Option A) is the standard approach. For locked bootloaders, you cannot flash modified signed images at all.

  8. 8. Troubleshooting

    ProblemFix
    avbtool: not an AVB imageImage is not AVB-signed (older Android). Skip footer removal.
    magiskboot unpack fails after footer removalTry AIK instead. Some vendor headers are non-standard.
    system.img won't mount after footer removalImage may still be sparse — run simg2img first.
    Ramdisk cpio is emptyOn Android 13+ GKI devices, ramdisk is in init_boot.img, not boot.img.
    Device bootloop after flashing modified imageAVB rejected it. Disable verity/vbmeta, or restore stock image.
    avbtool erase_footer failsImage may be truncated or corrupted. Re-extract from firmware.
    EROFS image won't extract with e2fsckEROFS needs fsck.erofs, not ext4 tools. See EROFS guide.

  9. 9. Complete command reference

    # ---- Check AVB footer ----
python3 avbtool.py info_image --image boot.img

# ---- Remove AVB footer ----
python3 avbtool.py erase_footer --image boot.img --output boot_unsigned.img
python3 avbtool.py erase_footer --image system.img --output system_unsigned.img

# ---- Unpack boot/recovery ----
mkdir boot_unpack && cd boot_unpack
magiskboot unpack boot_unsigned.img
mkdir ramdisk_out && cd ramdisk_out
cpio -idmv < ../ramdisk.cpio

# ---- Unpack system ----
# 1. Convert sparse to raw if needed
simg2img system_unsigned.img system_raw.img

# 2. Check filesystem type
file system_raw.img

# 3. Extract ext4
sudo mount -o loop,ro system_raw.img /mnt/system

# 4. Extract EROFS
sudo fsck.erofs --extract=./system_extract system_raw.img

# ---- Repack boot ----
magiskboot repack boot_unsigned.img new-boot.img

# ---- Flash with AVB disabled ----
fastboot --disable-verity --disable-verification flash vbmeta vbmeta.img
fastboot flash boot new-boot.img

# ---- Re-add AVB footer (requires OEM key) ----
python3 avbtool.py add_hash_footer \
  --image new-boot.img \
  --partition_name boot \
  --partition_size 33554432 \
  --key /path/to/key.pem

  10. 10. Best practices

    • ✅ Always keep the original signed image — you may need to restore it.
    • ✅ Use avbtool info_image first to confirm the footer exists.
    • ✅ Remove the footer before unpacking — otherwise unpackers read garbage.
    • ✅ For unlocked bootloaders, disable AVB rather than trying to re-sign [citation:15].
    • ✅ Check if the image is sparse before mounting — simg2img first.
    • ✅ On Android 13+, patch init_boot.img for ramdisk changes.
    • ✅ Never flash a modified signed image to a locked bootloader — it will always fail.

Tip: if your goal is simply to root the device, you do not need to unpack manually. Magisk's official patch method handles AVB and ramdisk modifications automatically. This guide is for advanced modification — editing ramdisk files, replacing adbd, or modifying system partitions.
